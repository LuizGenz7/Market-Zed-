1. PROJECT OVERVIEW
======================================================================

Build a production-ready Flutter mobile application for MarketZed, the Zambia-first marketplace already operating as a Next.js web application.

The Flutter app must provide the public marketplace experience for ordinary customers, buyers, sellers, job seekers and people making wanted requests. It must connect to the existing production backend and data. It is not a replacement for the website and must not create a second marketplace database.

The mobile application must:
- Run on Android and iOS from one Flutter codebase.
- Use the existing Firebase Authentication project.
- Read and write marketplace data through the existing trusted Next.js API routes and the existing Firestore public-read rules.
- Use the existing Cloudinary upload service for listing photos.
- Use the existing Lipila server-side payment integration for mobile-money payments.
- Display the same categories, listing data, prices, Zambian locations, promotion status and verification status as the website.
- Be mobile-first, fast, accessible and usable on modest Android devices and variable mobile internet connections in Zambia.
- Never expose server secrets, Firebase Admin credentials, Lipila API keys or Cloudinary API secrets in the Flutter application.

Important: the uploaded repository is the source of truth for the current web application. Where this document identifies a capability as not currently exposed through an API, do not invent a backend endpoint. Use the approved alternative described below or add a properly secured API to the existing Next.js backend before implementing that capability.

PRODUCT NAME: MarketZed
PRODUCT TYPE: Public mobile marketplace
PLATFORMS: Android and iOS

BACKEND: Existing Next.js App Router application
DATABASE: Existing Firebase Cloud Firestore
AUTHENTICATION: Existing Firebase Authentication
IMAGE STORAGE: Existing Cloudinary integration
PAYMENTS: Existing Lipila live mobile-money integration
CURRENCY: ZMW (Zambian Kwacha)

Use Firebase sendPasswordResetEmail or the appropriate FlutterFire method. Show a neutral confirmation so the user knows to check their email.

8.4 Token handling
For calls to protected Next.js API routes:
- Get the current Firebase user's ID token using Firebase Auth.
- Send Authorization: Bearer <Firebase ID token>.
- Refresh the token when Firebase indicates it is expired or invalid.
- Never store a service-account credential in the app.

8.5 Session cookie
The web app exchanges a Firebase ID token for an HttpOnly session cookie at POST /api/auth/session for browser sessions. A native Flutter app does not need to reproduce browser cookie handling if its protected API calls use the Firebase ID token and the existing requireUser middleware accepts bearer tokens. Confirm this behavior against the deployed API before release. Do not store or expose the session cookie manually in app code.

8.6 Email verification
The current web registration sends a verification email. The current posting permission is based on the server-side successful K30 payment and profile flags, not merely the email verification state. Keep these concepts separate in the UI.

10. ACCOUNT ACTIVATION AND K30 LIPILA PAYMENT
======================================================================

The current web product requires a one-time K30 payment to activate listing-posting access for ordinary listing categories.

Important exception:
- Wanted requests are free to publish and do not require the K30 posting activation fee.

10.1 Activation screen
Explain:
- One-time K30 account activation fee.
- Payment is made through mobile money using Lipila.
- User can choose their own mobile-money number or another person's number.
- The prompt is sent to the entered payer number.
- Payment ownership remains attached to the signed-in MarketZed account.
- Supported number format is Zambian +260 / 260 followed by 9 digits.
- Do not ask for or collect an NRC.
- Do not tell the user that a payment succeeded until the server verifies it.

10.2 Start payment

POST /api/payments/create

Authorization: Bearer <Firebase ID token>

JSON body:
{
  "purpose": "account_verification",
  "accountNumber": "260XXXXXXXXX",
  "payerType": "self"
}

payerType may be:
- self
- other

The API response may include:
- paymentId
- referenceId
- status
- message

The current API may return an existing pending payment instead of creating another one. Respect this response and allow the user to check the existing payment.

10.3 Check payment status

POST /api/payments/status

Authorization: Bearer <Firebase ID token>

JSON body:
{
  "paymentId": "<payment id>"
}

Possible statuses include:
- pending
- successful
- failed
- cancelled
- expired

The app must show:
- Pending: approve the mobile-money prompt on the phone, then check again.
- Successful: posting access is activated.
- Failed: explain that payment was declined and offer a retry when appropriate.
- Cancelled: explain cancellation and allow a new attempt.
- Expired: explain expiry and allow a new attempt.

The backend checks Lipila directly. The app must never call Lipila directly and must never mark a payment successful locally.

10.4 Server-side activation rules

Only after the backend confirms a successful payment with matching amount, currency and reference:
- payment status becomes successful.
- user verificationPaymentStatus becomes paid.
- postingEnabled becomes true.
- verified becomes true.
- verification notification is created.

The current one-time fee is K30. Never let the app send its own amount and have the server trust it. The backend determines the amount.

10.5 Payment safety
- Never collect mobile-money PINs.
- Never collect one-time passwords.
- Never store payment credentials.
- Do not show a success animation until the API returns successful.
- Handle network interruption while a payment is pending.
- Persist paymentId locally only as a convenience to resume checking; the server remains the source of truth.
- Avoid creating repeated payments when a pending payment already exists.

- If not activated, explain the K30 one-time activation and link to the activation screen.
- For category wanted, allow the free wanted-request flow for signed-in users without K30 activation, consistent with the server implementation.
- If profile lookup fails, show retry rather than assuming the user is verified.

Required:

- subcategory
- title
- description
- province
- town
- at least one contact method

Title:
- Minimum 4 characters.

Description:

Price:
- Optional.
- Numeric and non-negative.

Contact preferences:
- phone (optional individually)

- Phone and WhatsApp should validate Zambian numbers in the format +260XXXXXXXXX or 260XXXXXXXXX.
- Email must be valid.

Images:
- JPG, PNG or WebP only.
- Each file maximum 8 MB.
- Maximum 10 images.
- Normal categories require at least one image.

Every listing submission requires acceptance of the ownership/lawful-authority declaration.

Use the exact current declaration wording from the web posting form. The current declaration version is:
2026-11-16-v1

Submit:

- ownershipDeclarationVersion: "2026-11-16-v1"

Do not silently remove this declaration or change its version. If the web backend changes the declaration version, update the mobile app to match.

11.4 Image upload

Upload each image using:
POST /api/cloudinary/upload

Authorization: Bearer <Firebase ID token>
Content-Type: multipart/form-data
Field: file

The existing server:

- Limits upload rate to 30 per user per hour.
- Limits each file to 8 MB.
- Validates JPG, PNG and WebP file signatures.
- Uploads to the Cloudinary folder marketzed/listings.
- Returns URL, thumbUrl, publicId, width, height and format.

Use returned secure URL and thumbnail URL in the listing payload. Never put Cloudinary API secrets in Flutter. Do not upload directly using a secret embedded in the app.

- Pending review / live_needs_review
- Reviewed / live_reviewed
- Published
- Unavailable
- Fulfilled
- Hidden/removed where returned, with explanatory status and no republish action if backend disallows it.

12.3 Change availability

PATCH /api/listings/manage

Authorization: Bearer <Firebase ID token>

Body:
{
  "listingId": "<id>",
  "action": "mark_unavailable"
}

Allowed actions:
- mark_unavailable
- mark_available
- mark_fulfilled
- renew_wanted

Rules:
- User must own the listing.
- Hidden or removed listings cannot be republished through this endpoint.
- mark_fulfilled is only valid for wanted listings.
- renew_wanted is only valid for wanted listings.
- Fulfilled wanted requests cannot be renewed.
- Renewing a wanted request resets its expiry to 60 days and status to active.

12.4 Edit listing

POST /api/listings/revise

Authorization: Bearer <Firebase ID token>

Body:
{
  "listingId": "<id>",
  "changes": {
    "title": "...",
    "description": "...",
    "price": 100,
    "subcategory": "...",
    "categoryDetails": {},
    "images": [],
    "location": {
      "province": "Lusaka",
      "town": "Lusaka"
    },
    "contactPreferences": {}
  }
}

The backend allows only these change keys:
- title
- description
- price
- subcategory
- categoryDetails
- images
- location
- contactPreferences

Only live listings in moderation states live_needs_review, live_reviewed or published can be edited. The backend applies its own rules and may queue material changes for review. Show the returned result and never assume an edit was saved if the API fails.

======================================================================
13. WANTED REQUESTS
======================================================================

Wanted is a first-class category and has a special business flow.

- Wanted requests are free to publish.
- No K30 posting activation is required for wanted requests.
- Images are optional.
- Price is treated as a budget.
- Every wanted request requires at least one contact method.
- Wanted requests become publicly visible immediately after a valid submission.
- Wanted requests are created with active status and expire after 60 days.
- Users can mark their wanted requests fulfilled.
- Eligible unfulfilled wanted requests can be renewed for another 60 days.
- Fulfilled requests cannot be renewed; the user must create a new request.
- Promoted wanted requests may appear first.

Wanted details should make it easy for a person who has the requested item/service to contact the requester. Use the request's public contactPreferences.

Wanted listing cards should visibly use a WANTED label. Use “See More” or an equivalent clear detail action.

D. RECOMMENDED ALGOLIA SEARCH — PRODUCTION IMPLEMENTATION
Algolia is approved as a proposed search enhancement, but source repository has no Algolia implementation at the time of this spec. It must be added as a coordinated backend/web/mobile change, not assumed already live.

D1. Search architecture
- Flutter/Web public search clients -> Algolia Search API using a Search-Only key.
- Existing Next.js backend -> Algolia indexing Admin key server-only for indexing, updating, deletion, reindex and reconciliation.
- Firestore/MarketZed API remains source of truth; Algolia is a derived search index and never a database of record.

- Keep the Algolia Search-Only key public/mobile-safe. Never embed Admin API key, write key, service key, or privileged credentials in the web client or mobile binary. Use server-controlled secured keys only if user-specific filtering is genuinely required.

D2. Index schema (one shared public listing index, unless scaling evidence justifies partitioning)
- `objectID`: stable listing ID, identical to Firestore listing document ID.
- `title`, `description`, `categoryId`, `subcategory`, `categoryDetails`, `listingType`, `province`, `town`, `price`, `currency`, `priceMode`, `searchableTags`.
- `isPromoted`, `sellerVerified`, `moderationStatus`, `availabilityStatus`, `isPublic`, `publishedAt`, `createdAt`, `thumbnail`.
- Optional category-specific attributes only if public, validated, and useful to search.
- Do not index account email, contact phone/WhatsApp, private profile data, payment information, ownership-declaration metadata, admin notes, moderation reasons, private revisions or tokens.
- Index eligible public listings only. Filter hidden/removed, private, unavailable and fulfilled/expired wanted requests according to authoritative server rules. Do not index drafts or pending private content.
- Make promotion state and verified flags server-calculated. Do not accept a mobile or web client's boolean as authority.

D3. Index lifecycle, consistency and operations
- Add server-side index synchronizer triggered from the existing listing creation/edit/moderation/availability/fulfillment/removal/promotion workflows. It should be idempotent.
- Index only after committed Firestore changes. Prefer event/outbox/transaction-safe or durable job pattern with retries; no fire-and-forget losing updates. Handle partial failure and reconcile.
- On delete, hidden, removed, unavailable, fulfilled or expired (where applicable), remove or update the search object promptly so stale results are not returned. Listing mutations should invalidate server/web caches as already done.
- Provide safe full reindex and dry-run tools in admin/operator environment, not Flutter. Reconcile Algolia IDs against Firestore, retry failures, and log counts/errors. Never expose index admin actions to users.
- Search results are resolved by stable objectID and remain subject to backend eligibility. Detail API/web listing is authoritative. If the indexed result is stale, omit it or refresh from backend before showing a dangerous action.
- Indexing must include tests for create, edit, approval, moderation, hiding/removing, availability, promotion changes, wanted fulfillment/expiry, retry, duplicate events and reconciliation.
- Preserve existing backend exact-token search as a degraded/fallback mode during migration. Do not claim Algolia is operational until credentials, index, shared web/mobile search integration and synchronization are deployed and verified.

D4. Search UX and network efficiency
- Debounce typed queries ~300–400 ms; autocomplete begins after 2 characters; cancel or ignore superseded requests.
- Typo tolerance, prefix search, query suggestions, synonyms, relevant ranking, filters/facets, category/province/town, price range, sort and pagination.
- Five marketplace bottom tabs stay as specified. Search results remain compact two-column listing cards; filters are contextual to category.
- Search relevance must win: promoted listings receive a bounded boost only when they match the query; never let unrelated promoted ads override strong relevance.
- Store recent search history locally and allow clearing it. Cache small query/filter results with a freshness timestamp; keep old results visible while refreshing.
- Avoid per-keystroke requests, full index dumps, giant payloads, aggressive prefetch, full-size images or autoplay. Data Saver uses small transformed thumbnails, disables prefetch and nonessential refresh.
- Algolia plan starts on Free tier if within current plan quotas; monitor usage/record count and alert before upgrade. Plan limits and prices are subject to change and must be re-checked at deployment. No paid-plan assumptions are hardcoded in Flutter.
- Baseline observed for the Free plan during spec preparation: 10,000 search requests/month and 50,000 records. Grow and Grow Plus have additional usage pricing and features; verify live pricing/quota at setup. Start Free and alert/monitor usage before quota exhaustion.
