2. NON-NEGOTIABLE MARKETPLACE RULES AND PRIORITY
======================================================================

MarketZed is a discovery and contact marketplace. Users browse listings and contact owners/sellers directly. Do not introduce checkout, wallet, escrow, delivery or settlement functionality unless separately approved.

PROPERTY RULES:
- Property listings are FOR RENT ONLY.
- Allowed examples: houses, apartments, rooms, shops, offices, commercial premises and warehouses for rent.
- Land is completely excluded.
- No land sales, plot sales, land rental or land leasing.
- No property-for-sale transaction type.
- Enforce these rules in UI, domain/repository validation, queries, demo data, admin moderation and Firestore Security Rules wherever applicable. Hiding a category in the UI is not sufficient.

DISCOVERY PRIORITY:
- Products and approved marketplace categories are the primary purpose of MarketZed.
- Rental properties are also a major marketplace category.
- Wanted requests, jobs and services are secondary discovery content.
- Wanted, jobs and services use full-width single-column cards.
- In mixed Explore content, show a compact preview of one Wanted request, one latest Job and one Service, each with “View all”.
- Do not let secondary content displace product/property sections.
- Bottom navigation: Home, Explore, Post, Wanted, Account.
- Saved/Favourites belongs inside Account, not in bottom navigation.

3. FIX SESSION EXPIRY — APPROXIMATELY 30 DAYS
======================================================================

Current failure in My Listings:
“Couldn't load your listings. Your admin session has expired. Sign in again.”

Investigate the actual cause. Do not hide the error or endlessly retry.

Requirements:
- Persist valid sign-in sessions for approximately 30 days where supported by the existing identity architecture.
- Distinguish Firebase authentication state from any custom admin/API session. A client-side timer does not extend a server session.
- Prefer Firebase-supported authentication persistence and, if the architecture uses server session cookies, configure and validate an appropriate maximum lifetime (about 30 days).
- Refresh/reissue credentials securely where supported.
- Never store passwords, refresh tokens or long-lived secrets in plaintext preferences or logs.
- Use encrypted platform storage if sensitive local session material is required.
- On resume or before protected requests, validate/refresh the session through the supported flow.
- Distinguish network failure, offline cache, permission denied, revoked credentials and genuinely expired sessions.
- If truly expired/revoked, show a clear sign-in action and preserve screen context where possible.
- Admin access remains role-based and server/rules enforced. Longer sessions must not grant privileges.
- Users must never self-promote to admin.

Test app restart, process death, token refresh, expiry boundary, revoked credentials, offline use, disabled accounts and role changes. A valid user must not be repeatedly asked to sign in; a genuinely revoked session must be rejected.

8. FAST QUERIES, CACHE-FIRST DATA AND OFFLINE SUPPORT
======================================================================

Audit Firestore queries:
- Remove unbounded collection downloads.
- Use indexed, bounded queries, server-side filters where supported, cursor pagination and sensible page sizes.
- Avoid downloading all listings and filtering everything on-device.
- Centralize query logic in repositories/data sources.
- Prevent duplicate requests from recomposition/navigation.
- Debounce typing and cancel obsolete searches.
- Separate public marketplace cache policy from private account data.
- Document required Firestore indexes.

CACHE-FIRST UX:
- Immediately render valid cached data when a screen opens.
- Fetch fresh data in the background and update the UI.
- Use a subtle refresh indicator instead of replacing content with a full-screen spinner.
- Indicate stale/offline data where appropriate.
- Persist useful cache across app restarts.
- Handle invalidation, schema changes, sign-out and account switching.
- Never expose one user's private cached data to another user.

DRIFT / LOCAL DATABASE:
- Evaluate Drift only if compatible with the existing native stack. Drift is commonly a Dart/Flutter technology; do not add a Flutter/Dart layer to a Kotlin-only Android app just to use its name.
- For Kotlin/Jetpack Compose, prefer Room/SQLite unless the project already has a supported Drift integration.
- Cache appropriate public listing summaries, categories, recently viewed items, saved items and search history.
- Use DataStore for small preferences, not relational marketplace data.
- Define freshness timestamps, schema versioning and sync rules.
- Never cache payment credentials or raw authentication secrets.

OFFLINE:
- Browse previously cached data while offline.
- Show offline status without falsely claiming the session expired.
- Queue only safe, idempotent actions where appropriate.
- Never queue a payment as though it succeeded.
- Reconcile safe pending actions when connectivity returns.
- Handle conflicts and deleted/updated listings.

ALGOLIA:
- Evaluate current Algolia free-tier availability, limits, indexing/operation quotas, terms and pricing before adopting it. Do not assume a free tier is permanent or sufficient.
- If adopted, synchronize Firestore to the search index through trusted backend functions/server-side code.
- Never embed Algolia admin keys in the APK.
- If unsuitable, optimize Firestore search or propose an alternative.
- Document cost and scale assumptions.

10. GEMINI MARKETPLACE ASSISTANT
======================================================================

Add an optional Gemini assistant for practical marketplace help.

Example: “My budget is K5,000. What phone should I look for?”
The assistant must:
- Understand the stated ZMW budget.
- Search actual available listings using bounded, approved queries.
- Compare relevant listings by price, condition, location and known attributes.
- Explain trade-offs and suggest suitable results within/near budget.
- Link to real matching listings.
- Clearly separate real listings from general advice.
- Never invent stock, price, seller rating or availability.

Other uses:
- Refine search terms and filters.
- Explain listing attributes.
- Compare a small number of listings.
- Suggest questions to ask a seller.
- Help draft listing titles/descriptions without publishing automatically.
- Explain MarketZed features.
- Help users understand rental property options under the rent-only rule.

PERSONALIZATION:
- Adapt recommendations from explicit preferences and permitted marketplace interactions.
- Provide controls to inspect/disable/clear personalization.
- Do not infer sensitive traits.
- Do not claim the model trains itself on personal data. “Learning” means controlled preference/recommendation adaptation, not automatic model fine-tuning.
- Do not send passwords, tokens, payment data, private contacts or unnecessary personal data to Gemini.

SECURITY:
- Never put Gemini API keys in the APK.
- Route requests through a trusted backend.
- Enforce quotas, validation, rate limits and abuse protection.
- Validate structured model output before display/use.
- AI must never publish listings, contact sellers, make payments or change settings without explicit user action.
- Provide non-AI fallback and label AI suggestions.
